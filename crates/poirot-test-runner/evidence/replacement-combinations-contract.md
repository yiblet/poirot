# Combinations with replacement

COMBINA was absent from the registry. The original authored `COMBINA(4.23,3)` check expected 20 from the pinned ClosedXML assertion and independent Calc evidence. That check now passes under the suite's existing ExcelDocumentation policy; registering and implementing the function resolves it, not a policy change.

Microsoft's individual [COMBINA documentation](https://support.microsoft.com/en-us/excel/functions/combina-function) specifies truncation, nonnegative arguments, n>=k, NUM for domain errors, VALUE for nonnumeric input, and examples (4,3)=20 and (10,3)=220. The documented n>=k constraint is narrower than the abstract replacement identity. Calc 26.2.6.3 independently rejects n<k; this implementation honors the documented domain. It does not invent a former COMBINA source variant. Both builtin policies use this one new contract. Native Excel is unavailable.

Fresh probes distinguish operation order: Calc (3.2,3.8)=10, (0.2,0.8)=0, and negative fractions are errors. We reject raw negatives, truncate both operands, then compare. Calc (0,0)=0 and (0.2,0)=0 independently support zero available kinds producing zero. Omitted arguments and blank references supply zero; numeric text follows the existing metered locale-aware host parser. Logical operands supply zero/one. Both operands are converted in source order before domain validation, preserving errors such as (-1,1/0) producing DIV0. Calc emits VALUE for invalid numeric domains; Microsoft specifies NUM, which is the implemented contract.

Three options were compared before implementation: reuse the pinned combination kernel, log-gamma, and dynamic programming. Independent Calc (1000,200)=1.66768330678137e233 establishes a finite result. Existing COMBIN rejects its transformed pair (1199,200), because its explicitly pinned POI kernel rejects the smaller count above 170 and multiplies the numerator before factorial division. Direct reuse is disproved. Log-gamma would lose exact small-integer behavior; dynamic programming requires unnecessary storage/work. Replan: preserve COMBIN and use a general exact binomial primitive over complementary integer counts.

The primitive computes C(a+b,a), preserving counts as exact BigUint integers so forming n+k-1 cannot overflow or lose n-1 through floating cancellation. Its multiply/divide recurrence computes exact integers; binary64 rounding happens only at the end. Input bit lengths are checked locally at 1024. If both counts are >=1024, C(a+b,a)>=2^1024 proves finite binary64 overflow immediately. Otherwise there are at most 1023 iterations. Each intermediate is bounded at 2049 bits; values above 1024 bits after division prove overflow. Host work and collection admission occur before execution, and resource failures stay operational even inside IFERROR.

Independent Python `float(math.comb(1199,200))` is 1.667683306781366e233, used as an exact binary64 expectation in the kernel regression. It was not copied from Poirot or adjusted to Calc's decimal serialization. Small counts are independently checked by exhaustive subset enumeration, Pascal's identity, and symmetry. Additional tests cover domain/truncation, zero/one, transformed overflow, true overflow, pinned COMBIN stability, origins, error order, locale text, and operational limits.

Raw investigation probes and typed Calc observations are retained in `replacement-combinations-investigation-calc.json` and `replacement-combinations-order-calc.json`. Their placeholder expected zeros deliberately record observations rather than claim corroborated expectations. One extreme probe, (1E308,1E308), stalled Calc; its isolated process was terminated. No exact Calc result is asserted for that input. The implementation rejects its overflow by the proven bound. `replacement-combinations-libreoffice.json` freshly corroborates the changed original suite and binds its SHA256; prior reports are retained.
