# DATEDIF calendar interval contract

DATEDIF was absent from the executable registry. The new function has one contract under both builtin policies; there is no prior POI implementation to preserve or evidence supporting a policy distinction. Existing functions retain their policies. The original two ClosedXML calendar scenario names, formulas and expected values are unchanged; only their resolved known-gap annotations are removed. No scenario relocation was necessary.

Mode-specific calendar rules over civil-date primitives were selected. Serial-day division cannot distinguish completed months, leap-year anniversaries or residual intervals. A duration library would still require explicit compatibility rules. Serial truncation and unit parsing live in named central coercev2 requests; the kernel accepts typed units, epoch and bounded integer days. The new workbook-independent `poirot-functions-dates` crate contains only the new interval algorithm; unrelated evaluator date algorithms were not moved.

## Independent sources

- [Microsoft DATEDIF documentation](https://support.microsoft.com/en-au/excel/functions/datedif-function) defines Y/M/D/MD/YM/YD, accepts dates as serials, text or formula results, and specifies NUM for reversed dates. It warns about negative, zero and inaccurate MD results.
- [Pinned ClosedXML DateAndTimeTests](https://github.com/ClosedXML/ClosedXML/blob/09f2f21a60e821ce7fb18ca3576b272e5dd6d921/ClosedXML.Tests/Excel/CalcEngine/DateAndTimeTests.cs) supplies independent expected values for all six modes, pathological MD, leap-year YD, invalid units, bounds and reversed dates. Retrieved source SHA-256: `2a69e56f5414b4b4e41a5dc56c9b56311310a927339d2375af2682786ad5b368`.
- [Pinned ClosedXML implementation and DateParts](https://github.com/ClosedXML/ClosedXML/blob/09f2f21a60e821ce7fb18ca3576b272e5dd6d921/ClosedXML/Excel/CalcEngine/Functions/DateAndTime.cs) establishes completed-period rules, overflowing prior-month MD borrowing, start-year YD projection, serial zero as 1900-01-00, phantom 1900-02-29, and an early-calendar YD adjustment whose underlying Excel mechanism is unresolved. Retrieved SHA-256: `6ce5f733be5d9cc06f3335981925da405bde1d7534195ba308f70716826c1336`.
- `datedif-libreoffice.json` is fresh, source-hash-bound Calc evidence for the changed original suite and new neighboring suite. Older reports remain intact. `datedif-probes.json` retains discriminating raw observations across all modes, equal/reversed dates, fractional dates, early serials, leap days, month ends and argument types. Raw probes are observations rather than authored expectations.

## Rules and deliberate limits

Y counts completed anniversaries; M counts completed months; D subtracts truncated serial days. YM is the completed-month remainder. MD borrows from the month preceding the end date without clamping the start day, so 2020-01-31 to 2024-03-01 returns -1. YD projects the end month/day into the start year or following year. It does not use the end year's leap calendar. The historical early-1900 YD adjustment in ClosedXML is deliberately omitted: its author also describes the mechanism as undeciphered, and Calc disagrees with the single assertion. YD follows calendar projection; matching that undocumented early-1900 Excel quirk is outside the established supported contract.

Admission uses the shared central Calendar scalar request, existing finite numeric-text and date-text grammars, and host-metered text views. Arguments are consumed left to right; date bounds and ordering are checked after scalar admission and unit acquisition, consistent with the source signature adapter. Errors propagate during admission. Dates truncate fractions before ordering, so 1.9 to 1.1 is zero days. Units accept ASCII case variants without whitespace trimming and invalid units return NUM. Referenced text, numbers and units preserve their scalar identity until this request. Both date systems are covered; default-year/date-order effects remain lazy in the shared text resolver. Budget aborts remain operational under IFERROR.

Calc is corroboration, not an Excel oracle. It returns VALUE for reversed dates and invalid units, while Microsoft/pinned source specify NUM. Calc serial-zero MD for (0,61) is -1; pinned DateParts semantics produce 1 from 1900-01-00 to March 1. Calc returns 52 for YD(1900-01-12,1901-03-04); the pinned upstream assertion expects 51. That disputed assertion is retained as a documented limitation rather than introduced as a new unsupported scenario. The source-bound report corroborates 56 of 57 retained checks: YD(2000-02-20,2100-02-10) is 356 by the pinned start-year rule, while Calc returns 355. Both start-year leap and nonleap cases are retained unchanged to distinguish the rule; this disagreement is not hidden by adjusting expectations. Raw multi-error formulas can encounter Calc OOXML parsing differences (#NAME?); they do not establish evaluator error order. Native Excel was not run; MD's documented limitations and broader historical quirks are not claimed eliminated.

Registering the function and changing serialized enum identities invalidates both raw evaluator snapshots and public artifact semantics: raw VERSION 15 to 16, COMPATIBILITY_REVISION 16 to 17. The snapshot regression rejects the preceding version and retains durable source recovery.
